# Production Incident Playbook: 503 Errors, CI/CD Deploying Old Code & Midnight Debugging

## The Scenarios Nobody Teaches You — Until Production Breaks

---

It is 2 AM. Your phone is ringing. Users are reporting 503 errors. The CI/CD pipeline shows green — everything deployed successfully 20 minutes ago. But something is clearly wrong.

This is the moment where documentation written at 2 AM is worth nothing. What you need is a mental model — a systematic playbook that walks you from "something is broken" to "I know exactly what it is and how to fix it" in under 10 minutes.

This article covers two of the most common and most frustrating production scenarios:

1. **503 errors in production** — the service is "up" but users can't reach it
2. **CI/CD pipeline succeeds but old code is running** — the most confusing deployment failure

Both come with deep root-cause analysis, step-by-step commands, and interview-level Q&A.

## Part 1 — Production 503: Complete Troubleshooting Playbook

### What Does 503 Actually Mean?

```
HTTP 503 Service Unavailable

Generated by:   The load balancer or reverse proxy (NOT your application)
Meaning:        The upstream (your app/pod/instance) is not available to serve the request
NOT meaning:    Your application returned 503 — that would be an application-level error

503 from ALB/Nginx/Ingress = "I tried to forward this request but nobody answered"
```

### The 503 Decision Tree

```
User gets 503
      │
      ├── Is the load balancer healthy?
      │         │
      │    ALB returning 503?
      │    Check: AWS Console → Target Groups → Health Status
      │         │
      │    All targets unhealthy → go to App Layer
      │    Some targets healthy  → partial failure, go to Instance Layer
      │
      ├── Are pods/instances running?
      │         │
      │    kubectl get pods / aws ec2 describe-instances
      │         │
      │    All down → Deployment failure, OOM, crashed
      │    Some running → Readiness probe / health check failing
      │
      ├── Is the app listening on the right port?
      │         │
      │    kubectl exec -it <pod> -- curl localhost:8080
      │         │
      │    Connection refused → App not started or wrong port
      │    Returns 200 → App is fine, routing is the problem
      │
      └── Is traffic reaching the app at all?
                │
           Check ALB access logs, Nginx logs, Ingress logs
           Is request hitting the backend or being rejected at the edge?
```

### Step-by-Step 503 Investigation

#### Layer 1 — Verify the 503 Source

```bash
# Is the 503 from your ALB, Nginx, or Kubernetes Ingress?
# Check response headers — they reveal who sent the 503

curl -I https://yourapp.com/api/health
# HTTP/1.1 503 Service Unavailable
# Server: awselb/2.0          ← ALB is sending 503 (backend unhealthy)
# Server: nginx/1.21.0        ← Nginx/Ingress is sending 503
# Server: your-app/1.0        ← App itself returned 503 (different problem)

# ALB 503 = TargetGroup has no healthy targets
# Nginx 503 = upstream backend is down
# App 503 = application logic returned 503 (check app logs)
```

#### Layer 2 — Check ALB Target Health

```bash
# AWS CLI — check target group health
aws elbv2 describe-target-health \
  --target-group-arn arn:aws:elasticloadbalancing:region:account:targetgroup/name/id

# Output:
# TargetHealthDescription:
#   Target: i-0abc123 (or IP)
#   TargetHealth:
#     State: unhealthy
#     Reason: Target.FailedHealthChecks
#     Description: Health checks failed

# Kubernetes — check service endpoints
kubectl get endpoints my-service
# If <none> → No healthy pods are registered → All traffic fails → 503
```

#### Layer 3 — Check Pod Health in Kubernetes

```bash
# Are pods running?
kubectl get pods -n production
# Look for: CrashLoopBackOff, Error, OOMKilled, Pending

# Are pods READY? (Running ≠ Ready)
kubectl get pods -n production
# READY column: 0/1 = pod excluded from service endpoints → 503

# Why is readiness probe failing?
kubectl describe pod <pod-name> -n production
# Events: "Readiness probe failed: HTTP probe failed with statuscode: 503"
# Or:     "Readiness probe failed: connection refused"

# Test health endpoint directly from inside the pod
kubectl exec -it <pod-name> -n production -- curl -v localhost:8080/health
# If this returns 200 but readiness probe fails → probe config is wrong (wrong port/path)
# If this also fails → app is not healthy
```

#### Layer 4 — Check Application Logs

```bash
# Current logs
kubectl logs <pod-name> -n production

# Logs from the crashed container (most important during 503)
kubectl logs <pod-name> -n production --previous

# Follow logs in real time while reproducing the 503
kubectl logs <pod-name> -n production -f

# All pods of a deployment
kubectl logs -l app=my-app -n production --all-containers

# AWS CloudWatch Logs (ECS or EC2)
aws logs filter-log-events \
  --log-group-name /ecs/my-app \
  --start-time $(date -d '10 minutes ago' +%s000) \
  --filter-pattern "ERROR"
```

#### Layer 5 — Check Resource Exhaustion

```bash
# Are pods being throttled or OOMKilled?
kubectl top pods -n production
# CPU: 950m/1000m (95% throttled — requests are timing out → 503)
# Memory: 490Mi/512Mi (near limit — about to OOMKill)

# Check recent OOMKills
kubectl get events -n production --sort-by='.lastTimestamp' | grep OOMKill

# Check node pressure
kubectl describe node <node-name> | grep -A10 Conditions
# MemoryPressure: True → node is evicting pods → 503
# DiskPressure: True → pods can't start → 503
```

#### Layer 6 — Check Ingress and Networking

```bash
# Is Ingress routing correctly?
kubectl describe ingress my-ingress -n production
# Look for:
#   Rules:
#     Host: myapp.com
#     Path: /api/*
#     Backend: my-service:8080    ← Is this the right service and port?

# Is the service port correct?
kubectl describe svc my-service -n production
# Port: 80/TCP → TargetPort: 8080/TCP
# Endpoints: 10.0.0.5:8080,10.0.0.6:8080   ← Should have IPs here

# NetworkPolicy blocking traffic?
kubectl get networkpolicy -n production
kubectl describe networkpolicy <name>

# DNS resolution inside cluster
kubectl exec -it <any-pod> -- nslookup my-service.production.svc.cluster.local
```

#### Layer 7 — Check ALB Health Check Configuration

```bash
# Mismatch between ALB health check path and actual app health endpoint
# is one of the most common 503 causes after a deployment

# ALB health check configured to: GET /health  → returns 200
# After deployment, health endpoint moved to: GET /api/health → returns 404
# ALB marks target unhealthy → 503 for all traffic

# Fix: Update health check path in ALB target group
aws elbv2 modify-target-group \
  --target-group-arn <arn> \
  --health-check-path /api/health

# Or check in Terraform:
resource "aws_lb_target_group" "app" {
  health_check {
    path    = "/api/health"   # Must match what your app actually serves
    matcher = "200"
  }
}
```

### Common 503 Root Causes — Quick Reference

| Root Cause | How to Detect | Fix |
|---|---|---|
| All pods in CrashLoopBackOff | `kubectl get pods` | Fix crash (check logs --previous) |
| Readiness probe wrong path/port | `kubectl describe pod` events | Fix probe config |
| Zero endpoints in service | `kubectl get endpoints` → `<none>` | Fix label selector |
| OOMKilled pods | `kubectl describe pod` → Exit Code 137 | Increase memory limit |
| ALB health check path changed | ALB → Target Groups → Health checks | Update health check path |
| New deployment broke the app | Compare deploy time with 503 start time | `kubectl rollout undo` |
| Node disk/memory pressure | `kubectl describe node` → Conditions | Free space / add node |
| NetworkPolicy blocking ingress | `kubectl describe networkpolicy` | Update policy rules |
| CPU throttling causing timeouts | `kubectl top pods` → near CPU limit | Increase CPU limit or scale out |
| Database connection pool exhausted | App logs: "too many connections" | Add RDS Proxy, tune pool size |

### 503 During a Deployment — The Most Common Midnight Scenario

```
Timeline:
  23:45 — CI/CD pipeline starts deployment
  23:50 — Pipeline shows success ✅
  23:51 — Users start reporting 503 ❌
  23:52 — Your phone rings ☎️

What happened:

Scenario A: New version is crashing
  New pods start → crash immediately → CrashLoopBackOff
  Kubernetes keeps old pods running (rolling update safety)
  BUT: If deployment was fast and maxUnavailable is too high,
       some old pods may have been killed before new pods passed health checks

Diagnosis:
  kubectl get pods -n production       # New pods in CrashLoopBackOff?
  kubectl rollout status deployment/app # Rollout stuck?
  kubectl logs <new-pod> --previous    # What's the new version crash?

Fix:
  kubectl rollout undo deployment/app  # Immediate rollback to last version
  kubectl rollout status deployment/app --watch  # Watch it roll back

Scenario B: Deployment succeeded but health check path changed
  New code changed /health to /api/v2/health
  ALB health check still pings /health → 404 → marks unhealthy → 503

Diagnosis:
  aws elbv2 describe-target-health --target-group-arn <arn>
  # State: unhealthy, Reason: Target.FailedHealthChecks

Fix (immediate):
  aws elbv2 modify-target-group --target-group-arn <arn> --health-check-path /api/v2/health
  # Wait 2-3 health check intervals (30-60 seconds)
  # Targets become healthy → 503 resolves

Scenario C: Database migration in new deployment locked tables
  New deployment ran migration that locked production tables
  App is running but all DB queries hang → requests timeout → 503

Diagnosis:
  Check DB: SHOW PROCESSLIST; (MySQL) or SELECT * FROM pg_stat_activity; (PostgreSQL)
  Look for: Waiting for metadata lock, Lock wait timeout exceeded

Fix (immediate):
  kubectl rollout undo deployment/app   # Roll back, release migration locks
  Plan: Run migrations separately, before deploying new code
```

## Part 2 — CI/CD Success But Old Code Running

### Why Does This Happen?

This is one of the most confusing production problems because everything looks correct — the pipeline is green, the deployment event shows success, but users are clearly hitting the old version.

```
CI/CD says: ✅ Deployed successfully
Reality:    🔴 Old code is running

Possible causes ranked by frequency:

1. Image cached — :latest tag, pod never pulled new image
2. Deployment not actually updated — same image digest, no rollout triggered
3. Wrong cluster / namespace — deployed to staging instead of production
4. Old pods not terminated — deployment uses wrong update strategy
5. CDN caching — CloudFront serving old HTML/JS to users
6. Multiple deployments — traffic split between old and new pods
7. Sticky sessions — users pinned to old pod instances
8. Feature flags — new code deployed but feature still disabled
```

---

### Step-by-Step Debug: Old Code Running After Successful Deploy

#### Step 1 — Confirm Which Code is Actually Running

```bash
# Call a version endpoint on your app (you should always have one)
curl https://yourapp.com/api/version
# {"version": "1.2.3", "commit": "abc1234", "deployedAt": "2024-01-15T23:45:00Z"}

# If no version endpoint, check a known changed behavior
# Or add X-Version header in your app:
# response.headers['X-App-Version'] = process.env.APP_VERSION

curl -I https://yourapp.com/api/health
# X-App-Version: 1.2.2   ← Old version, not 1.2.3 you just deployed
```

#### Step 2 — Verify the Correct Image is Running in Kubernetes

```bash
# What image are pods actually running?
kubectl get pods -n production -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[0].image}{"\n"}{end}'
# Output:
# my-app-7d4f8b-abc12   myrepo/myapp:1.2.2   ← OLD image
# my-app-7d4f8b-def34   myrepo/myapp:1.2.2   ← OLD image

# What image does the deployment THINK it should run?
kubectl get deployment my-app -n production -o jsonpath='{.spec.template.spec.containers[0].image}'
# myrepo/myapp:1.2.3   ← Deployment has new version

# Pods have old image but deployment has new image = rollout didn't happen or got stuck
kubectl rollout status deployment/my-app -n production
# Waiting for rollout to finish: 0 out of 3 new replicas have been updated

# Force the rollout:
kubectl rollout restart deployment/my-app -n production
```

#### Step 3 — Check the :latest Tag Problem

```bash
# Is your deployment using :latest tag?
kubectl get deployment my-app -n production -o yaml | grep image:
# image: myrepo/myapp:latest   ← PROBLEM

# :latest with imagePullPolicy: IfNotPresent (default):
#   Kubernetes pulls image once, caches it on the node
#   New push to :latest on registry → Kubernetes never re-pulls
#   Same image tag = no new rollout triggered
#   Old code stays running indefinitely

# Fix 1: Use explicit version tags (permanent fix)
image: myrepo/myapp:1.2.3

# Fix 2: Force pull every time (slower deployments, not recommended for prod)
imagePullPolicy: Always

# Fix 3: Force pod recreation (immediate fix for current situation)
kubectl rollout restart deployment/my-app -n production
```

#### Step 4 — Check if Deployment Was Applied to the Right Context

```bash
# Which cluster are you connected to right now?
kubectl config current-context
# Output: production-cluster-ap-south-1   ← Correct
# Or:     staging-cluster-ap-south-1      ← WRONG — you deployed to staging!

# List all contexts
kubectl config get-contexts

# Switch to production
kubectl config use-context production-cluster-ap-south-1

# Which namespace did CI/CD deploy to?
# Check your CI/CD pipeline config — most common mistake is:
# - CI deploys to 'default' namespace
# - Your app runs in 'production' namespace
# - Deployment exists in default, app in production → nothing changes in production

kubectl get deployment my-app -n default    # The one CI/CD updated (wrong)
kubectl get deployment my-app -n production # Your actual app (unchanged)
```

#### Step 5 — Check for CDN Caching Old Frontend

```bash
# Backend API returning new code, but users still see old UI
# → CloudFront or CDN is serving cached old HTML/JS files

# Check cache headers on your HTML
curl -I https://yourapp.com/
# Cache-Control: max-age=86400    ← Cached for 24 hours!
# X-Cache: Hit from cloudfront    ← Confirmed: CloudFront is serving cached content

# Fix 1: Invalidate CloudFront cache immediately
aws cloudfront create-invalidation \
  --distribution-id EDFDVBD6EXAMPLE \
  --paths "/*"                  # Invalidate all files (costs money per path)
# or
  --paths "/index.html" "/static/js/*"  # Invalidate specific files

# Fix 2: Use cache-busting in your build (permanent fix)
# Instead of: /static/app.js
# Use:        /static/app.abc123.js   (hash changes every build)
# CloudFront caches the hashed file, but index.html always points to latest hash
```

#### Step 6 — Check Image Digest (Not Just Tag)

```bash
# Two builds can produce different images but use the same tag
# The digest (SHA256) is the true unique identifier

# What digest is in ECR for :1.2.3?
aws ecr describe-images \
  --repository-name myapp \
  --image-ids imageTag=1.2.3 \
  --query 'imageDetails[0].imageDigest'
# sha256:abc123def456...

# What digest is the running pod using?
kubectl get pod <pod-name> -n production -o jsonpath='{.status.containerStatuses[0].imageID}'
# docker-pullable://myrepo/myapp@sha256:abc123def456...   ← Same digest = correct image
# docker-pullable://myrepo/myapp@sha256:xyz789old000...   ← Different digest = old image!

# Pin your deployments to digest for guaranteed version:
image: myrepo/myapp@sha256:abc123def456...   # Unambiguous — always this exact image
```

### CI/CD Pipeline Debug — Common Advanced Scenarios

#### Scenario: Pipeline is green but Kubernetes never got the new image

```bash
# CI/CD pipeline steps:
# 1. Build → ✅
# 2. Push to ECR → ✅
# 3. kubectl apply -f deployment.yaml → ✅ (command succeeded)
# 4. But deployment.yaml still has old image tag!

# Why: CI/CD applied the YAML file from the repo
#      But nobody updated the image tag in the YAML file
#      kubectl apply → "no changes, deployment unchanged"

# Fix: CI/CD must update the image tag before applying
# Option A: sed replacement in pipeline
sed -i "s|IMAGE_TAG|${BUILD_VERSION}|g" deployment.yaml
kubectl apply -f deployment.yaml

# Option B: kubectl set image (no YAML editing needed)
kubectl set image deployment/my-app \
  my-container=myrepo/myapp:${BUILD_VERSION} \
  -n production

# Option C: Helm (values.yaml updated by CI)
helm upgrade my-app ./chart \
  --set image.tag=${BUILD_VERSION} \
  -n production
```

#### Scenario: Pipeline green but deployment rollout never completed

```bash
# CI/CD ran kubectl apply → returned 0 (success)
# But it only means "API accepted the update" — not "pods are running"
# The rollout is async — pipeline exited before checking if rollout succeeded

# Fix: Add rollout status check to CI/CD pipeline
kubectl apply -f deployment.yaml
kubectl rollout status deployment/my-app -n production --timeout=300s
# This BLOCKS until rollout completes (all pods updated) or times out
# Exit code 0 = rollout complete ✅
# Exit code 1 = rollout failed/timed out ❌ (pipeline fails, team gets notified)

# GitHub Actions example:
- name: Deploy to Kubernetes
  run: |
    kubectl apply -f k8s/deployment.yaml
    kubectl rollout status deployment/my-app -n production --timeout=5m
    echo "Deployment complete — all pods running new version"
```

#### Scenario: Canary deployment — some users on old code, some on new

```bash
# You have two deployments:
kubectl get deployments -n production
# my-app-stable    3/3   (old version, getting 90% traffic)
# my-app-canary    1/1   (new version, getting 10% traffic)

# User complains about seeing old UI:
# They might be hitting the stable deployment — this is by design

# To check which deployment a pod belongs to:
kubectl get pod <pod-name> -n production -o jsonpath='{.metadata.labels}'
# {"app":"my-app","version":"stable"}   ← old version pod, expected behavior

# To promote canary to stable (complete rollout):
kubectl scale deployment my-app-canary --replicas=4 -n production
kubectl scale deployment my-app-stable --replicas=0 -n production
# Now all traffic goes to new version

# Or use Argo Rollouts / Flagger for automated canary management
```

### The 2 AM Checklist — Fastest Path to Resolution

When you get paged at 2 AM with 503 or old code running, run these in order:

```bash
# ═══════════════════════════════════
# 503 CHECKLIST (run top to bottom)
# ═══════════════════════════════════

# 1. Is it a deployment that just happened?
kubectl rollout history deployment/my-app -n production
# If yes → kubectl rollout undo deployment/my-app -n production (IMMEDIATE FIX)

# 2. Are pods running and READY?
kubectl get pods -n production
# If CrashLoopBackOff → kubectl logs <pod> --previous
# If READY 0/1 → kubectl describe pod <pod> (readiness probe)

# 3. Are there endpoints?
kubectl get endpoints my-service -n production
# If <none> → selector mismatch or no ready pods

# 4. Is the app responding inside the pod?
kubectl exec -it <pod-name> -n production -- curl localhost:8080/health

# 5. Are resources exhausted?
kubectl top pods -n production
kubectl top nodes

# 6. Check events for clues
kubectl get events -n production --sort-by='.lastTimestamp' | tail -20


# ═══════════════════════════════════
# OLD CODE CHECKLIST
# ═══════════════════════════════════

# 1. What image is actually running?
kubectl get pods -n production -o jsonpath='{range .items[*]}{.spec.containers[0].image}{"\n"}{end}'

# 2. Did rollout complete?
kubectl rollout status deployment/my-app -n production

# 3. Is :latest tag the issue?
kubectl get deployment my-app -n production -o yaml | grep image:

# 4. Is CDN caching old content?
curl -I https://yourapp.com/ | grep -E "X-Cache|Cache-Control"

# 5. Are you in the right context/namespace?
kubectl config current-context
kubectl get deployment my-app -n production
```

## Interview Q&A — Scenario-Based

### Q: ALB shows targets as healthy but users still get 503. Where do you look?

```
When ALB health checks pass but 503 persists:

1. Application-level 503: App is returning 503 to health check path too
   but returning 503 for actual business logic paths
   Check: curl pod-ip:8080/api/users (not just /health)

2. Health check path is different from actual traffic path
   ALB checks /health → 200 OK
   User hits /api/v2/data → 503 from app (different code path failing)

3. Partial failure — one or two targets unhealthy
   ALB considers target group healthy even if some targets are unhealthy
   Check: describe-target-health → some targets still showing unhealthy

4. Downstream dependency failing (not the app itself)
   App returns 503 because its database/cache is unavailable
   Check: application logs for "connection refused" or "timeout" to DB/Redis

5. TLS/SSL issue
   ALB HTTPS → EC2 HTTP works
   But if you configured ALB → EC2 HTTPS, certificate mismatch → 503
```

### Q: Your deployment rolled back automatically. How do you find out why?

```bash
# Kubernetes auto-rollback doesn't happen by default — you configured it
# OR the rollout is just stuck (not rolled back)

# Check rollout history
kubectl rollout history deployment/my-app -n production

# Check what triggered the rollback in CI/CD
# Most CI systems (GitHub Actions, ArgoCD) log rollback events

# If using ArgoCD:
argocd app history my-app                # Full deployment history
argocd app get my-app                    # Current sync status

# If Kubernetes just stopped the rollout (not rolled back):
kubectl rollout status deployment/my-app
# "Waiting for rollout to finish: 1 out of 3 new replicas updated"
# Paused because new pods are unhealthy

kubectl get pods -n production
# 2 old pods Running, 1 new pod CrashLoopBackOff
# Kubernetes stopped here — didn't rollback, didn't proceed

# Your options:
kubectl rollout undo deployment/my-app          # Manual rollback
kubectl rollout resume deployment/my-app         # Resume if you paused it manually
```

### Q: How do you ensure a deployment only succeeds if the application is actually healthy?

```bash
# The naive approach (wrong):
kubectl apply -f deployment.yaml
# Returns 0 immediately — deployment object created, but pods not checked

# The right approach: block until rollout completes
kubectl apply -f deployment.yaml
kubectl rollout status deployment/my-app --timeout=300s
# Fails if pods don't become Ready within 300 seconds

# Even better — automated smoke test after deployment:
kubectl apply -f deployment.yaml
kubectl rollout status deployment/my-app --timeout=300s

# Wait for DNS/LB to propagate (usually 15-30 seconds)
sleep 30

# Smoke test the actual endpoint
RESPONSE=$(curl -s -o /dev/null -w "%{http_code}" https://yourapp.com/api/health)
if [ "$RESPONSE" != "200" ]; then
  echo "Smoke test failed — rolling back"
  kubectl rollout undo deployment/my-app
  exit 1
fi
echo "Deployment verified — health check passing"

# Production-grade: use readiness gates, progressive delivery (Argo Rollouts)
# that automatically roll back if error rate exceeds threshold
```

## Key Takeaways

- **503 = load balancer has no healthy targets** — it never means "the load balancer is broken"
- **Running ≠ Ready** — a pod can be Running but excluded from service endpoints due to failing readiness probe — this is the single most common cause of post-deployment 503
- **Always rollout undo first, investigate second** — in a midnight incident, restore service before root-causing
- **Never use :latest in production** — it makes deployments non-deterministic and debugging impossible
- **`kubectl rollout status --timeout`** must be in every CI/CD pipeline — without it, success means "API accepted the request," not "users can access the app"
- **CDN invalidation is often the missing step** — backend deploys fine, but users see old frontend because CloudFront cached it
- **Check the right namespace and cluster context** — more deployments fail silently in the wrong namespace than engineers admit
- **Image digest is the ground truth** — tags are mutable, digests are not. When in doubt, compare SHA256 digests
